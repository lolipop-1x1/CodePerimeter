# 运行时性能排查与路径优化

日期：2026-10-07
状态：路径优化、合成回归、后台更新与真实复测已完成；CPU 有小幅下降，write 来源仍占用较高 CPU，部分来源延迟超过 3 秒。

## 范围

针对采集器与分析进程持续占用 CPU 的反馈，先测量运行中的事件量、处理耗时和来源延迟，再用匿名合成事件验证可优化的路径。保留所有进程的监控范围、四组来源订阅、证据语义及持久化要求。

真实环境仅提取进程角色和数值统计；原始进程采样位于项目外的私有临时目录，不进入本规格或 Git。未成功获取有效调用栈，不能据此认定线上 CPU 的函数占比。

## 当前结论

- 两个连续约 10 秒的 CPU 时间采样中，分析进程约占用 61%–66%，write 来源的 eslogger 约占用 62%–63%；不是只有截图中的瞬时峰值。
- 一次约 10 秒的来源计数差为 104,794 个事件，其中 write 为 82,647 个。该窗口只是当前工作负载样本，不是固定事件速率。
- 更新前的来源运行中仅持久化 865 条匹配事件，其他大量系统事件仍需要解析和路径判断。该计数不是数据库历史总量。
- 初次核查 write 来源到接收延迟约 33 分钟，后续核查约 43 分钟；同时 exec、read、activity 的后续样本延迟为 3–9ms。零本地丢帧计数不代表来源没有积压，历史 activity 序列缺口仍需单独保留。
- 最初的实时采样来自旧后台程序，未包含本次路径优化；不能将合成基准的改善直接换算成真实进程 CPU 降幅。更新前的新采样和部署状态见验证记录。
- 更新并恢复既有 FDA 后，六个约 10 秒窗口中分析进程 CPU 为 55.0%–59.1%，write eslogger 为 52.9%–56.3%。前后加权平均单帧 Host 耗时从 50.81µs 降至 41.42µs；实际工作负载未完全固定，不能将全部降幅归因于代码修改。
- 新来源样本的 write 延迟为 1,676–14,477ms，其余三组为 1–254ms；后续窗口约 14 秒，写入积压仍然存在。重启改变了来源排队状态，不能将旧约 89 分钟积压的消失归因于路径优化。
- 匿名真实复测中，批量访问、tar 命令、ZIP 输出告警均可查询，系统通知发送回执在工作负载启动后 301–677ms 返回。三个样本不能证明所有写入场景均满足 3 秒目标。

## 实施

旧路径规范化在完整路径不存在时逐级查询父目录。匿名符号链接加 24 层缺失目录的回归用例产生 26 次文件系统查询。

保留现存路径及短缺失路径的逐层快速返回。连续五个路径前缀均因不存在或非目录而无法解析时，二分查找可解析祖先并补回缺失后缀。其他错误保持原来的逐级回退；不使用跨事件符号链接缓存。

## 验证

1. 性能回归测试先在旧实现失败：深层缺失路径产生 26 次查询；最终优化将上限约束为 12 次，符号链接目标与缺失后缀保持一致。
2. 中间版本的短缺失路径产生 5 次查询，比原来的 3 次更多；新增测试捕获此退化，最终版本保持 3 次。覆盖非目录前缀与二分遇到权限错误后的逐层回退。
3. 四路来源各使用独立序列，每次 10,000 个 2KiB 合成事件；其中 40 个匹配目录。核对各类型观察、过滤、持久化数量，零丢帧、零重复、零数据库缺口。
4. 比较普通路径与深层缺失路径；分别在每 250ms 和每 33ms 请求一次状态的配置下运行。实际请求频率受处理时长和结尾查询影响，不视为严格恒定频率。
5. 完整 Rust 回归与静态检查，详见 [验证记录](validation.md)。

## 后续

- 安装版已与新 Release 哈希一致，三个后台角色已重启。用户已恢复安装版采集器既有 FDA 授权，真实复测期间四组事件持续接收，数据库与两项有效监控目录保留。
- 写入来源的大量 JSON 序列化、传输和分析需要独立继续测量；路径优化不直接改变系统 eslogger 的序列化实现。
- 本机 eslogger 的 `--select` 按程序可执行路径前缀选择事件，不能作为监控文件目录的过滤参数。不能为降低 CPU 擅自限制为少数进程。
- 写入积压期间，归档输出事件的及时发现不能按 3 秒目标宣称通过。
