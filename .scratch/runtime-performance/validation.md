# 路径优化验证

日期：2026-10-07
范围：匿名合成处理链、代码回归、后台更新与恢复既有 FDA 后的真实 CPU、来源延迟及告警复测。

## Release 基准

同一台机器、每次 10,000 个事件，使用独立临时目录、数据库、控制 socket 与合成来源；未使用真实采样数据。前后单独执行对应测试，表中为各一次样本，非统计显著性或实际 CPU 验收。

| 路径与状态查询配置 | 优化前事件/秒 | 优化后事件/秒 | 优化前 Host 平均耗时 | 优化后 Host 平均耗时 |
| --- | ---: | ---: | ---: | ---: |
| 普通路径、250ms 查询间隔 | 37,305 | 37,384 | 16.5µs | 15.5µs |
| 普通路径、33ms 查询间隔 | 51,635 | 47,014 | 15.5µs | 16.1µs |
| 深层缺失路径、250ms 查询间隔 | 7,538 | 18,961 | 117.9µs | 45.9µs |
| 深层缺失路径、33ms 查询间隔 | 8,426 | 19,242 | 115.9µs | 49.2µs |

深层缺失路径的 Host 平均耗时下降约 58%–61%。吞吐读数包含结束状态查询的等待，不能只据此推算纯 CPU 处理能力；普通路径未显示同等幅度的改善，33ms 查询配置的后样本略低于前样本。

中间版本更早进入二分查找，在深层场景曾达到约 26,100 事件/秒，但让短缺失路径从 3 次查询变成 5 次。最终版本保留短路径快速返回，以上表格使用修正后的实现，不使用中间版本的最佳数字作为交付结果。

每次基准均核对 10,000 个观察事件、40 个持久化事件、9,960 个过滤事件，以及零丢帧、零重复、零数据库缺口。深层缺失路径主要用于检验昂贵的目录外匹配；不证明真实事件具有相同路径分布。

## 可复现命令

```sh
cargo test --release --locked --lib path_performance_tests -- --nocapture
cargo test --release --locked --test runtime_host four_stream_deep_missing_paths_host_throughput -- --exact --nocapture
cargo test --release --locked --test runtime_host four_stream_ten_thousand_frame_host_throughput_with_status_polling -- --exact --nocapture
cargo test --release --locked
cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings
```

socket 测试需在允许本机 Unix socket 的普通用户环境执行。此测试不启动真实 ES 客户端，不安装或授权后台服务。

## 回归结果

- 最终完整 Rust Release 回归：197 项通过，2 项专用入口按原约定忽略。
- 路径性能回归、符号链接解析、非目录前缀和权限错误回退通过。
- `cargo fmt --check` 与 `cargo clippy --locked --all-targets -- -D warnings` 通过。
- 后台程序已更新并恢复真实采集；实际 CPU 与单帧处理耗时有下降，但写入来源 CPU 仍偏高，部分来源延迟超过 3 秒。

## 后台更新与真实复测

用户要求更新后台程序并查看优化效果。安装与启用均通过产品现有系统授权接口完成；管理员密码不进入网页或对话。

- 更新前两个约 10 秒窗口：分析进程 CPU 为 61.0% / 59.4%，write eslogger 为 59.1% / 57.5%；Host 平均耗时为 47.7µs / 54.4µs，处理速率为约 10,629 / 9,206 帧每秒。
- 更新前 write 来源延迟约 89 分钟；read、exec、activity 的样本延迟为 7–252ms。此前历史 read/activity 序列缺口保留，不能按零缺口描述。
- 安装与启用操作均返回成功；安装二进制与刚构建的 Release 哈希一致。采集、分析、通知三个角色已重启，数据库与两项有效监控目录保留。
- 更新后曾报告 `permission_denied`，没有使用未采集时的低 CPU 作为性能改善证据。系统设置中已核实安装版对应第一个同名权限项，用户随后恢复该项既有 FDA，eslogger 项保持开启。
- 恢复后四组来源持续接收事件，三个后台角色运行、数据库就绪；以下采样窗口中进程均未重启，本地丢行、读端丢帧、数据库缺口及新来源序列缺口计数为零。旧来源历史缺口不因此清除。
- 重启会改变来源运行与排队状态，旧 write 积压中的未转发事件可能被丢弃，数量未知。恢复后的来源低延迟不能直接归因于路径优化，也不能当作旧积压完整重放的证据。

## 真实 CPU 与来源延迟

更新前两个、更新后六个约 10 秒窗口，使用 CPU 时间增量计算区间占用。CPU 的 100% 对应一个逻辑核心。后六个窗口分三段测量，并非完全连续；三个匿名冒烟场景在第二段与第三段之间执行。期间未暂停来源、减少订阅或改变监控目录。

| 指标 | 更新前 | 更新后 |
| --- | ---: | ---: |
| 分析进程区间 CPU | 59.4%–61.0% | 55.0%–59.1% |
| write eslogger 区间 CPU | 57.5%–59.1% | 52.9%–56.3% |
| 分析进程加权平均 CPU | 60.2% | 56.5% |
| write eslogger 加权平均 CPU | 58.3% | 54.8% |
| Host 加权平均每帧耗时 | 50.81µs | 41.42µs |
| 平均处理量 | 9,915 帧/秒 | 9,534 帧/秒 |
| write 占帧数比例 | 76.5% | 75.5% |
| write 来源到接收样本延迟 | 约 89 分钟 | 1,676–14,477ms |

每帧 Host 平均耗时下降约 18%，分析进程平均 CPU 下降约 4 个百分点。更新后事件速率约低 4%，来源比例接近，但事件路径分布和后台工作负载未完全固定；这是一组实际运行对比，不能作为严格受控的因果实验。write 来源仍持续占用约半个核心，本次路径优化未解决这条链路的整体成本。

更新后 read、exec、activity 的窗口末尾延迟为 1–254ms。write 的前四次延迟读数为 6,944、1,676、6,964、4,377ms；后续复核为 13,630ms，再测两个窗口为 14,477、14,298ms，写入积压仍然存在，不能宣称全链路 3 秒目标已通过。这里只记录窗口末尾样本，未计算来源延迟的分位数。

write eslogger 的 RSS 从更新前约 814–943MiB 降至更新后约 77–275MiB，最后两个窗口从约 214MiB 升至约 275MiB；同时分析进程 RSS 从约 17MiB 升至约 66–69MiB。来源已重启，且 RSS 不等于完整内存占用；不能将来源内存变化单独归因于路径优化。

## 匿名真实告警复测

在既有有效匿名测试目录内创建独立临时子目录，不改目录或规则配置。每个场景使用独立进程，按其进程身份及启动时间查询告警和通知反馈；完成后只删除本次创建的临时文件，两项有效监控目录保留。

| 场景 | 结果 | 告警首次查询可见上界 | 通知发送反馈 |
| --- | --- | ---: | ---: |
| 同一进程访问 60 个文件后在内存压缩 | 批量文件访问告警，60 个不同文件 | 138ms | 356ms |
| tar 打包明确项目输入 | 归档命令告警 | 309ms | 677ms |
| 同一进程读取项目文件并生成 ZIP | 归档输出告警 | 138ms | 301ms |

两个耗时均从合成工作负载启动计算，因触发发生在启动之后，是这三个样本从触发到查询可见／发送反馈的保守上界。查询可见时间含轮询与 API 开销，不等于内部告警生成时间；发送反馈不替代用户确认实际到屏。内存压缩场景仍只报告批量文件访问，不确认观察到了压缩操作。此次为部署后的三个冒烟场景，未重跑全部 14 个命令的 92 项验收。
