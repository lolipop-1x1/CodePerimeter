# 经验与历史实验

整理日期：2026-10-03。本文记录旧原型的可复用证据与约束，CodePerimeter 不继承旧任务的完成状态、实现进度或发布承诺。

## 已有决定性实验

旧原型代码基线为 `230ffe4`。实验在本机合成环境使用固定发送器、实际 HTTPS 检查网关和自建回环 HTTPS 接收端，没有运行真实 Agent 或上传用户项目。

| 步骤 | 历史结果 |
| --- | --- |
| 构造项目快照 | 32 个固定合成源码文件在内存归档、压缩并 AES-GCM 加密，生成 335 字节密文 |
| 构造合法请求 | 密文 Base64 编码后放入合法模型 JSON 的文本字段 |
| 未批准发送 | 网关返回 403，接收端没有新增禁止载荷，拒绝依赖批准门槛 |
| 明确批准接收方和该请求 | 网关返回 200，接收端收到相同正文，解码、认证解密与解压后恢复全部 32 个文件 |

它证明批准控制可以在该合成入口工作，也暴露了内容识别对合法文本中的密文快照的缺口。这不是未经批准的自动绕过，不证明真实客户端的出口已经受控。

原有“伪装 JSON”实验给原始密文字节声明 JSON 类型，因格式解析失败而拒绝。该结果仅支持格式检查，不能记为“识别了加密整仓上传”。

历史报告和代码基线可以帮助重建实验。旧构建目录中的结果文件不随本次迁移携带，当前没有重跑该实验；后续复现应保存发送器、配置、实收记录、校验与版本，使他人能独立判断结果。

## 旧原型未关闭的核心缺口

- 真实客户端的全部目标出口尚未强制接入检查入口。
- 正常原始请求的接入、认证和流式行为没有形成完整证明。
- 未知来源、已有连接、后台进程和旁路路径的实际覆盖不充分。
- 检查与执行层故障时持续阻止的能力没有成立的完整系统证据。
- 受限回环网关实验不能代表真实服务兼容或通用防护。

这些是历史缺口，不能仅用“本机缺少签名”解释所有问题。

## 对新项目的约束

| 经验 | 后续工作要求 |
| --- | --- |
| 组件可构建、测试通过仍可能缺少实际接入 | 先做一条贯穿真实观察、控制和接收结果的闭环 |
| 文件事件、打包迹象和上行量可以误报 | 正常索引、搜索、构建和本地打包与风险样本一起验 |
| 策略返回阻止不等于系统阻止 | 区分决定与执行反馈，并由接收端裁决合成载荷 |
| 默认拒绝陌生请求不等于识别密文 | 单独验证新目的地、获准服务和合法字段中的密文 |
| 全量放行获准域名会扩大内容缺口 | 接收方批准与内容批准独立，能力缺口可见 |
| 多平台抽象容易先于核心价值 | 从 Mac 真实调用者抽取小 Interface，迁移时复用规则和验收场景 |
| 地图和历史会话容易造成外发错觉 | 按 [指标口径](design/product-and-metrics.md) 展示不同证据 |
| 开源项目可下载不代表修改版免授权 | 官方发行包与本项目修改版分别评估运行、签名、许可和分发 |

继续投入的门槛见 [核心验收方案](validation/core-validation.md)。未通过时，集中关闭核心缺口或明确调整范围，避免以更多界面、票据或平台构建替代防护进展。
